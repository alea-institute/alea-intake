<objective>
Fix the asyncpg "another operation is in progress" bug that takes the dev Postgres
down (it fires even on the health-check SELECT 1). Two-part fix, verified locally
against a real PostgreSQL before any Railway work:

1. Add `pool_pre_ping=True` + `pool_recycle=1800` to the Postgres branch of the
   engine factory so poisoned/dead pooled connections are validated and recycled
   before reuse (addresses the symptom and stops the pool from re-handing-out a
   broken connection).
2. Root-cause fix: `_run_parallel_jurisdictions` fans branches out via
   `asyncio.gather`, and every branch drives the SHARED `self._session` (one asyncpg
   connection) — both through the stage instances (`_get_stage_instance` passes
   `db_session=self._session`) AND through the orchestrator's own checkpoint writes
   (`self._session.add(stage_record)` / `flush` in `_execute_stage_inner`). asyncpg
   connections are NOT concurrency-safe, so this code path NEVER worked on Postgres —
   it only survived on the demo's SQLite (aiosqlite serializes internally). The fix is
   to SERIALIZE the branches (await each in sequence instead of `asyncio.gather`),
   which restores correctness with a one-line change and no cross-session/ORM-detachment
   risk. True per-jurisdiction parallelism (per-branch connections + cross-session merge
   of the run/iteration objects) is a deliberate follow-up, not this phase.

Purpose: A poisoned shared connection persists in the pool and breaks unrelated
requests (including /health), so this is the root blocker for making dev healthy on Postgres.
Output: Engine factory hardened; orchestrator parallel path serialized; both
verified against a real local PostgreSQL.
</objective>
