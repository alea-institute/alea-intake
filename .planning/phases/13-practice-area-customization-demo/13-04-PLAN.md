## Database service — dedicated for demo (decision confirmed 2026-05-06)

Spin up a **separate** `alea-intake-demo-db` Postgres service so demo activity (audience suggestions, throwaway sessions, generated YAMLs) cannot contaminate `alea-intake-dev`.

```bash
railway add \
  --service alea-intake-demo-db \
  --image pgvector/pgvector:pg17 \
  --variables "POSTGRES_USER=alea" \
  --variables "POSTGRES_DB=alea_intake" \
  --variables "POSTGRES_PASSWORD=$(openssl rand -base64 24 | tr -d '/=+' | head -c 32)"
# Service is private-only by default — no public domain needed.
```

App env vars then point at this dedicated DB via the `${{alea-intake-demo-db.*}}` references in the next section.

## Create the app service via Railway CLI

```bash
cd "/home/damienriehl/Coding Projects/alea-intake"
railway link --project alea-tools

# Create the new service. Railway 4.x: railway service create OR add via dashboard then add --service.
# Verify CLI command name with `railway service --help` first; older docs used `railway add`.
railway service create alea-intake-demo  # OR `railway add --service alea-intake-demo` if that's the active syntax

# Point it at the demo branch on GitHub. This wires auto-deploy on push.
# CLI may not support source config in 4.31 — if not, configure in dashboard:
#   Service → Settings → Source → connect repo + set branch = demo/practice-customization
#   Service → Settings → Source → root directory = / (Dockerfile at repo root)
#   Service → Settings → Build → Dockerfile path = Dockerfile

# Set env vars (mirror alea-intake-dev exactly — see reference_railway_deploy.md memory)
railway variables --service alea-intake-demo --set "ALEA_DB_HOST=\${{alea-intake-demo-db.RAILWAY_PRIVATE_DOMAIN}}"
railway variables --service alea-intake-demo --set "ALEA_DB_PASSWORD=\${{alea-intake-demo-db.POSTGRES_PASSWORD}}"
railway variables --service alea-intake-demo --set "ALEA_DB_PORT=5432"
railway variables --service alea-intake-demo --set "ALEA_DB_USER=alea"
railway variables --service alea-intake-demo --set "ALEA_DB_NAME=alea_intake"
railway variables --service alea-intake-demo --set "ALEA_MASTER_KEY_PATH=/app/backend/data/master.key"
railway variables --service alea-intake-demo --set "ALEA_SKIP_MIGRATIONS=true"

# Generate domain so we know the URL, then set CORS / frontend base after.
railway domain --service alea-intake-demo
# Capture the URL it prints (likely alea-intake-demo-production.up.railway.app)

DEMO_URL="https://<paste-the-url-railway-printed>"
railway variables --service alea-intake-demo --set "ALEA_CORS_ORIGINS=[\"$DEMO_URL\"]"
railway variables --service alea-intake-demo --set "ALEA_FRONTEND_BASE_URL=$DEMO_URL"
railway variables --service alea-intake-demo --set "ALEA_OAUTH_REDIRECT_BASE_URL=$DEMO_URL"
```

**Important quirks (per `reference_railway_deploy.md`):**
- `ALEA_CORS_ORIGINS` must be a JSON array string, not comma-separated.
- `${{RAILWAY_PUBLIC_DOMAIN}}` resolves empty until `railway domain` runs — set CORS / frontend / oauth URLs **after** domain assignment.
- Healthcheck path is `/health`, not `/healthz` (already correct in `railway.toml`).
- First build is 15–20 min (torch, faiss, sentence-transformers, weasyprint). Plan around it — kick off the deploy as soon as the branch is pushable.

## Smoke-test checklist

Once the service shows `running`:

```bash
# 1. Healthcheck up
curl -f "$DEMO_URL/health" && echo "HEALTH OK"

# 2. Practice areas endpoint returns PI
curl -s "$DEMO_URL/api/practice-areas" | jq '.practice_areas[].id'
# Expect: "personal_injury"

# 3. Create a PI session
curl -s -X POST "$DEMO_URL/api/sessions" \
  -H 'content-type: application/json' \
  -d '{"practice_area_id":"personal_injury","mode":"consumer"}'
# Expect 200 + session JSON with practice_area_id echoed
```

Then, **using MCP chrome-devtools** (per global instructions — never headless CLI):
1. `navigate_page` → `$DEMO_URL`
2. `wait_for` → welcome card visible
3. `take_screenshot` → save to `$HOME/demo-baseline.png`, read it, confirm chip-row + Generic + Personal Injury chips are visible
4. Click `Personal Injury` → `take_screenshot` → confirm welcome copy changes to PI welcome
5. Open the chat → send "I was rear-ended last Tuesday" → confirm follow-up question is PI-flavored (mentions injuries / insurance / damages — not generic "tell me more")
6. Delete screenshots after inspection

## Rollback / contingency

- **If the build fails:** Railway keeps the previous deploy serving. Check logs, fix on branch, push.
- **If env vars are wrong:** `railway variables --service alea-intake-demo --set K=V` and trigger a redeploy.
- **If the demo URL is unstable just before talk:** worst case, point Damien to `alea-intake-dev` and walk through the architecture diagram. CONTEXT.md commits to PI on the demo URL as the primary fallback — that's what this plan delivers.
