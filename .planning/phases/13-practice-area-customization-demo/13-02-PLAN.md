# 13-02 — Session ↔ practice-area binding + HTTP surface

## Goal

Connect the registry from 13-01 to (a) the session model, (b) a `GET /api/practice-areas` endpoint, (c) `POST /api/sessions` so callers can create a session bound to a practice, and (d) the `ConversationService` so generated welcomes and follow-ups use the practice's `system_prompt` and `welcome_message_*` when set.

## Files to modify

- `backend/app/models/` — find the session model (likely `session.py` or under `models/intake/`). Add column:
  - `practice_area_id: Mapped[str | None] = mapped_column(String(64), nullable=True)`
  - Index it (`index=True`) so list queries by practice are cheap later.
  - Project uses `create_all` on startup (per `ALEA_SKIP_MIGRATIONS=true`), so no Alembic migration required — but **do** add the column nullable so existing rows don't break.
- `backend/app/services/intake/session_service.py` — `create_session()` now accepts `practice_area_id: str | None`. Validate against `app.state.practice_areas` registry; raise 400-equivalent domain error if id is unknown.
- `backend/app/services/intake/conversation.py`:
  - `ConversationService.__init__` accepts a `PracticeAreaRegistry | None`
  - `generate_response` — if a `practice_area_id` is provided (new optional kwarg), look it up and use its `system_prompt` instead of `INTAKE_SYSTEM_PROMPT`. Falls back to `INTAKE_SYSTEM_PROMPT` if registry is None or id missing.
  - `generate_welcome_message` — if `practice_area_id` is provided, return `welcome_message_consumer` or `welcome_message_professional` from the practice; otherwise current `_CONSUMER_WELCOME` / `_PROFESSIONAL_WELCOME`.
- `backend/app/api/` — find the routes that handle session creation (look for `POST` to `/sessions` or similar; likely `routes/intake.py` or `routes/sessions.py`).
  - Extend the request model to include optional `practice_area_id: str | None`
  - Pass through to `session_service.create_session`
- Wherever the websocket / chat handler invokes `ConversationService`, pass the session's `practice_area_id` through.

## Files to create

- `backend/app/api/routes/practice_areas.py`
  - `GET /api/practice-areas` → returns `[{id, display_name, disclaimer}]` sorted by `display_name`
  - **No** auth required for the list endpoint — practice areas are public taxonomy, the audience interacts unauthenticated
  - Reads from `request.app.state.practice_areas`
  - Register the router in the FastAPI app (find existing router registration, add this alongside)
- `backend/tests/test_practice_areas_api.py`
  - `GET /api/practice-areas` returns 200, list contains `personal_injury`, payload has the three documented fields, sorted by display_name
  - Sessions API: creating a session with `practice_area_id="personal_injury"` succeeds, response echoes the id
  - Sessions API: creating a session with `practice_area_id="not_a_thing"` returns 400 (or whatever the domain-error→HTTP mapping is — match existing patterns)
  - Sessions API: creating a session with no `practice_area_id` still works (backwards compatible)
- `backend/tests/test_conversation_practice_area.py`
  - `ConversationService.generate_response` with PI `practice_area_id` uses PI system prompt (assert by inspecting the prompt argument passed to LLM mock)
  - `generate_welcome_message` with PI returns the PI welcome string for consumer + professional modes
  - With no `practice_area_id`, falls back to `INTAKE_SYSTEM_PROMPT` and the original welcome strings (regression guard)

## Implementation notes

- **Don't** rename or split `INTAKE_SYSTEM_PROMPT` — keep it as the generic fallback. The two paths (generic vs practice-bound) coexist.
- **Discovery first:** before editing, run `grep -rn "ConversationService\|create_session\|INTAKE_SYSTEM_PROMPT" backend/app backend/tests` to locate the exact integration points. The current grep shows only 3 references but there's more wiring under `message_pipeline.py`.
- **Schema:** if the project uses `app/db/schemas` Pydantic models for API requests/responses, add `practice_area_id` there too. Keep request and response schemas symmetric.
- **Frontend contract** (locked here so 13-03 has no ambiguity):
  - `GET /api/practice-areas` → `{ practice_areas: [{ id: string, display_name: string, disclaimer: string | null }] }`
  - `POST /api/sessions` request body now accepts `practice_area_id: string | null`
  - Session response includes `practice_area_id: string | null`
